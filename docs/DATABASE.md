# Database

This is the definition of the conditioning tracker's database. The SQLAlchemy models in
`backend/app/models.py` implement it. The single migration `backend/alembic/versions/0001_initial.py`
creates it from those models and adds the audit trigger. `backend/tests/test_stack_edits_and_ids.py`
checks the key rules below. If any of the three disagrees with this page, that is a bug.

PostgreSQL 18, one database per installation (`fabric_conditioning` on the Mac). Nothing else
writes to it: the Pis, staff browsers and scripts all go through the HTTP API.

## Keys

- **Every generated key is a sequential integer.** It is a PostgreSQL identity column
  (`bigint GENERATED BY DEFAULT AS IDENTITY`). Nothing in the schema is a UUID.
- **Short text keys chosen by people:** rooms (`shared`), stations (`shared-door`) and
  treatments (`AR`, `5L`, ...).
- **A number is never issued twice.** That holds across restores too (see Backups).
- **Retry IDs** for scans and prints are `<client>-<n>`, for example `shared-door-118` or
  `print-7`. The client is a station id, or `print` for the label dialog. The server hands
  out `n` in blocks through `POST /api/request-ids`, so a browser whose storage was cleared
  still never reuses one.

## Tables

| Table | Key | What a row is | Changes after insert? |
| --- | --- | --- | --- |
| `rooms` | `id` text | A conditioning room and its target conditions | Seeded at startup |
| `stations` | `id` text | A door scanner, tied to one room | Seeded at startup |
| `treatments` | `code` text | A treatment name as written on prep sheets | Insert only |
| `projects` | `id` serial | A project number (unique; kept as text, so `000123` stays `000123`) | Insert only |
| `materials` | `id` serial | A material / sample reference (unique) | Insert only |
| `prep_drafts` | `id` serial | A prep sheet under review: `headers` per worksheet, then `rows`, one per sheet row (`schemas.PrepSheetRow`) | Edited until registered, then frozen (`committed`); `revision` refuses stale saves |
| `stacks` | `id` serial | One registered group: project, material, test, treatment | Project/material/test/treatment can be corrected (audited); `version` bumps on every change |
| `specimens` | `id` serial | One physical piece. **`id` is the label**: printed as id + Damm check digit. `number` is its place in the stack (01, 02, ...) | `revision`, `last_event_id`, `removed_at` |
| `conditioning_sessions` | `id` serial | A specimen's one ENTRY/EXIT period in a room | Exit time, corrections, `voided` by undo |
| `request_counters` | `client` text | The last retry number issued to a station or to `print` | Only increases |
| `movement_requests` | (`station_id`, `number`) | The stored result of one scan request, so a retry returns it | Insert only |
| `print_jobs` | `number` | One label print request (`print-<number>`) and what CUPS said | Status updated as CUPS answers |
| `audit_events` | `id` serial | Everything that happened, in order | **Never: append-only** |

### Rules the database enforces

- `specimens (stack_id, number)` is unique, and `number > 0`.
- One live conditioning period per specimen (`one_conditioning_period_per_specimen`). At most one
  open period per specimen (`one_open_session_per_specimen`). Exit is never before entry.
- `specimens.last_event_id` references `audit_events.id`. Undo and edit compare it with the event
  being changed to detect later activity.
- `audit_events` has a statement trigger that raises on `UPDATE`, `DELETE` and `TRUNCATE`.

### Numbers that are never reused

- A specimen keeps its id (its label) forever. Editing a stack never changes a specimen's id or
  number, so printed labels stay valid.
- Added specimens continue after the stack's highest number. That includes removed ones: if #02
  was removed, the next one added is #06, not #02.
- A removed specimen keeps its row and history (`removed_at` is set). Scanning its label is refused
  with "removed from stack N".

## Append-only history

`audit_events` is the record of what happened. Each row has a `kind`:

| kind | Written by |
| --- | --- |
| `registration` | Registering a prep sheet (one per stack) |
| `movement` | A scan, or a staff "missed scan" entry |
| `modification` | A staff edit of a movement (`payload.event_id` points at it) |
| `undo` | Undoing a movement (`payload.event_id` points at it) |
| `correction` | Older-style session corrections (`POST /api/corrections`) |
| `stack_edit` | Correcting project, material, test or treatment (`payload.changes` has before/after) |
| `specimens_added`, `specimens_removed` | Changing a printed stack's pieces |
| `label_print_requested`, `label_print`, `label_print_status` | Label printing |

Movement-type events store full `before` and `after` snapshots of the affected specimens' periods.
Any period can be rebuilt from the history alone. Current-state tables (`conditioning_sessions`,
`specimens`, `stacks`) are a fast view of the same facts. They may be corrected; the history is not.

## Backups

A backup (`backend/app/backups.py`, format 2) is a ZIP of `manifest.json` and `snapshot.json`.

- **What it holds:** every row of every table above, read in one `REPEATABLE READ` transaction, so
  the copy is consistent. That includes prep drafts, request counters, stored scan results and
  print jobs. It also holds the Alembic revision and a SHA-256 of the snapshot.
- **What it does not hold:** backup settings, the station configuration on each Pi, and anything
  outside PostgreSQL.
- **Names:** `fabric-20261112T070000123456.zip`, from the UTC time it was made.
- **Restore** loads the snapshot into a new database, which applies all the constraints above,
  then swaps it in. The previous database is kept, and a backup of it is taken first.
- **Counters never go backwards.** Before the swap, every identity sequence is moved past the
  highest number the running database has issued, and every `request_counters` row keeps the larger
  of its two values. So after restoring yesterday's backup, today's printed labels and the
  kiosks' reserved retry numbers can't be issued again.
- Archives in format 1 (the UUID schema) are refused.

## Changing the schema

There was no production data before sequential IDs, so the old UUID database was not migrated.
The schema starts from the single `0001_initial` migration. From now on, a schema change needs:

1. the model change,
2. a new Alembic migration after `0001_initial` (no more `create_all`),
3. an update to this page, and
4. a backup format bump if columns change, so old archives are refused or converted on purpose.

To start over with an empty database on the Mac (test data only):

```sh
python3 deploy/macos/host.py stop
PGPASSWORD=... psql -h 127.0.0.1 -p 55432 -U fabric -d fabric_conditioning -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
python3 deploy/macos/host.py start      # runs the migration
```
